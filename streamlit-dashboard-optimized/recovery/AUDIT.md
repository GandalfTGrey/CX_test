## NFS 约束下的开销

`data.py:59–65` 对每个目录完整枚举并排序；`data.py:68–77` 对每个标记目录执行 9 次 `Path.exists()`。即使只需要一个实验，也会先扫描其他实验和 checkpoint。对于 NFS，这些操作可能涉及远端目录枚举、属性查询与客户端属性缓存；不能将每次 Python 调用直接等同于一次网络往返，但大量元数据操作确实是当前读取路径必须优先削减的风险。

`load_records` 串行读取，并对每个结果重复探测最多 4 个元数据路径；相同实验的元数据 stat 没有去重。读取时还检查结果文件是否被替换或写入，这种一致性保护应保留，但应避免重复查询同一个文件。

目录缓存 10 秒过期，缓存键包含 `(root, pattern, refresh_token)`。切换任务或文件名、过期后再次交互，都会触发新的扫描。手动刷新生成的新 token 还会使未变化 JSON 的旧缓存无法命中。缓存命中能减少部分解析，但不是稳定的目录索引。

AgGrid 的每页 50 行仅是浏览器分页：完整 DataFrame 和 CSV 仍在服务端构造。它不能降低 NFS 读取量或完整结果传输量。

目前没有用户真实目录的数量、大小分布、权限、软链接布局与阶段计时，也没有 NFS 服务端负载、客户端缓存命中或网络测量。因此**不声称已定位真实加载失败的唯一原因，也不编造真实耗时或提速倍数**。

## 建议：NFS 只读数据源 + 本地 SQLite 索引

SQLite 数据库放在应用服务器的**本地磁盘**，例如通过 `DASHBOARD_INDEX_DIR` 配置；不要放进 NFS 数据目录，也不要把 SQLite WAL 当成多主机共享协调机制。Python 3.8 自带 `sqlite3`，无需更换运行环境或引入独立数据库服务。

数据路径分成三层：

1. **发现与索引。** 单个后台索引任务扫描 NFS，保存数据源、实验、checkpoint、文件名、路径、大小、mtime_ns、标记、索引批次与错误。枚举目录时同时识别标记文件，减少额外 exists；元数据按目录去重。明确支持原版软链接布局，记录目标和异常，以访问过的目标集合防止循环。第一次索引有真实成本，界面必须显示阶段、已扫描目录数、已发现结果数和耗时。
2. **查询。** 页面首先查询 SQLite 中已经完成的索引批次，通过实验、任务文件名、最新 checkpoint、标记和分页选择必要记录，再读取 NFS payload。趋势先从索引选择实验和 checkpoint 范围，再读对应结果；从源头消除“加载全部后再选 12 个”的顺序问题。
3. **结果与缓存。** 按路径及文件指纹缓存已读取结果或所需指标，设置字节预算而不只限制条目数。刷新先更新索引，仅对改变的文件失效缓存。CSV 使用当前查询定义并按需生成，避免每次交互重复构造完整导出。

索引更新采用单写者、小批事务和已完成批次标识。新扫描尚未完成时，页面继续使用上一份成功索引；新批次成功后再切换。权限失败、挂载暂时不可达或扫描取消时，保留旧结果并显示其时间及错误，不将“本次没有读到”当成“全部已删除”。只有成功完成相关范围扫描后才确认删除。

后台线程或任务只访问文件、SQLite 和进度队列，不直接调用 Streamlit UI 或修改界面 session state。界面负责轮询进度、展示取消请求和完成状态，兼容 Streamlit 1.40.1。NFS 系统调用阻塞时，线程取消不能立即中断该调用，应显示“已请求取消，等待当前 I/O 返回”，不能虚假显示已停止。

NFS 上不能依赖 watchdog / inotify 可靠发现其他机器的全部写入。采用有节制的周期核对、用户主动刷新与可选生产端清单；目录 mtime 不能单独证明已有文件内容未变。保留读取前后指纹检查、单文件错误隔离，并将索引时刻和结果新鲜度显式展示。

## 实施优先序

1. **诊断可见。** 在扫描开始前显示状态；输出结构、软链接、数量、字节和预算命中情况，分别计时扫描、筛选、读取、解析、渲染。区分无匹配、结构不支持、部分失败与预算拒绝。
2. **恢复基本可用性。** 处理原版软链接布局；将整批归零改为分页、按需读取与单文件错误隔离。大文件要明确报告或走选定指标提取，不能静默丢掉同批正常文件，也不能直接无限制读入内存。
3. **本地索引与渐进加载。** 同一根目录共享索引，提前筛选实验与 checkpoint，去除重复扫描和标记探测；当前查询与上一份成功结果分离。
4. **完整操作反馈。** 区分待应用条件、当前生效条件；提交后显示条件变化、阶段进展、完成结果和失败原因；失败时保留旧表并标明旧数据时间。
5. **视觉与交互。** 以数据源健康、当前查询、执行状态、结果和诊断组织页面；验收必须包括加载中、部分成功、空结果、失败四种状态，不能只展示理想静态截图。

## 复现命令与边界

`tests/test_loading_regressions.py` 是**现有实现的缺陷特征测试**。它们通过表示上表行为得到复现，不表示缺陷已经修好。后续生产实现修复后，应修改相应断言以验证期望的新行为，不应为了让这些测试继续通过而保留缺陷。

此测试依赖被审查项目源码和其现有依赖，不能脱离该项目单独运行。目录可以这样放置：

```text
work/
├── optimized_dashboard/       # 被审查的原项目
└── dashboard_recovery/
    ├── AUDIT.md
    └── tests/test_loading_regressions.py
```

在 `dashboard_recovery` 目录执行：

```bash
PYTHONPATH=../optimized_dashboard python -m unittest discover -s tests -p test_loading_regressions.py -v
```

如果原项目在别处，将 `PYTHONPATH` 替换为其实际绝对路径。测试默认也会查找脚本文件 `parents[2] / 'optimized_dashboard'`，没有硬编码工作区路径。测试只在系统临时目录创建少量构造 JSON 与软链接，完成后清理；不上传临时 fixture 或真实数据。没有权限创建软链接的系统会跳过对应两项测试。

本次在 Python 3.8.18 环境验证 8 项测试通过，无跳过。该测试结果只证明确定性的代码行为，不作为 NFS 性能基准。
